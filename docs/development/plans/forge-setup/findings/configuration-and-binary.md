## Gaps (design vs code), for the planner
- **G1.** The split "temper-service checks its part, the other crates theirs" has no mechanism: `Named` exposes no forges/identities/setup, `What` is closed, and `setup`/`setup.*`/`box.*` are refused by the strict reader. Needs a pass-through (opaque `setup` member, unclaimed overrides) and a shared problem form (`Problems::jig` takes only jig's `What`; `Against` is temper-service's).
- **G2.** "Checks steps 1-3 for every command" (configuration.md 8): in code the channel/identity/agent/memory checks run after the files are read (`startup.rs:198-248`); `sign-in` stops at `named`. `forge`/`box` read no secrets, so they too can only stop at `named`.
- **G3.** The pin: design says `temper-forge-forgejo`; code and forgejo-17's rules say the test crate; the process tier and the conformance tool read the throwaway's.
- **G4.** Dependencies: `temper-forge-setup` lists `skein-lib`, `skein-json` and `temper-forge-forgejo` (protocol.md 5), but jig's readers and `Path` come from `jig-protocol-config`; `temper-box`'s host needs `skein-shell` (`Host`, signals), not listed.
- **G5.** Bounds absent: the `small` numbers of all 15 new limits; `Step`'s fields and `steps`' signature; `owned.runner` `labels`/`capacity`/`path` limits; `bot.email` form; the `state` file's format; how the box finds the `temper` binary (current exe?) and an absolute CONFIG path.
- **G6.** configuration.md 10's examples are untested and the standalone one does not parse on main (`webhooks: null` is refused). Nothing says where the owned example is stored as a file.
